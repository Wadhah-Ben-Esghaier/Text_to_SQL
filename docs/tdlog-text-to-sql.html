2La première marche, pour le 23 novembre

Pas toute l'application : la fondation. Une grammaire écrite, un lexer et un parser pour un petit sous-ensemble de SQL, et une exécution en lecture seule sur Chinook. Pas encore de LLM. Comptez environ 3 heures par personne.

Les données : la base Chinook

Où la trouver, à quoi elle ressemble

Où : dans le dépôt lerocha/chinook-database, rubrique Releases, le fichier Chinook_Sqlite.sqlite (environ 1 Mo). C'est un seul fichier SQLite : rien à installer, Python sait le lire avec sqlite3. Mettez-le dans data/.

À quoi elle ressemble : un magasin de musique en ligne, 11 tables.

Album (347) → Artist (275) Track (3 503) → Album, Genre (25), MediaType (5) InvoiceLine (2 240) → Track, Invoice (412) Invoice → Customer (59) Customer → Employee (8) PlaylistTrack (8 715) → Track, Playlist (18) Employee.ReportsTo → Employee

Entre parenthèses, le nombre de lignes. Une flèche va de la table qui contient la clé étrangère vers la table qu'elle désigne : Album.ArtistId désigne une ligne de Artist.

Comment l'utiliser

À la main d'abord : sqlite3 data/Chinook_Sqlite.sqlite, puis .tables (liste des tables) et .schema Invoice (colonnes et clés). Écrivez 5 requêtes vous-mêmes avant d'écrire le parser.

Depuis Python, toujours en lecture seule (mode=ro) :

import sqlite3

def describe_chinook(path: str) -> tuple[list[str], list[str]]:
    connection = sqlite3.connect(f"file:{path}?mode=ro", uri=True)
    tables = [row[0] for row in connection.execute(
        "SELECT name FROM sqlite_master WHERE type = 'table'")]
    columns = [row[1] for row in connection.execute(
        "PRAGMA table_info(Invoice)")]
    return tables, columns

Exécuté : 11 tables ; colonnes d'Invoice : InvoiceId, CustomerId, InvoiceDate, BillingAddress, BillingCity, BillingState, BillingCountry, BillingPostalCode, Total.

Ce même schéma servira plus tard deux fois : votre vérificateur l'utilisera pour savoir si une table ou une colonne existe, et le prompt du LLM le contiendra.

Ce que doit faire votre programme

$ uv run t2s parse "SELECT FirstName, LastName FROM Customer LIMIT 5" Select(columns=['FirstName', 'LastName'], table='Customer', where=None, limit=5) $ uv run t2s parse "SELECT FROM Customer" ParseError: token 1: expected a column or table name, got 'FROM' $ uv run t2s run "SELECT FirstName FROM Customer WHERE Country = 'France' LIMIT 3" Camille Dominique Marc $ uv run t2s run "DELETE FROM Customer" refused: token 0: expected SELECT, got 'DELETE'

Exemple de sortie ; les noms de commandes sont libres. Les trois prénoms sont les vrais premiers clients français de Chinook.

Le sous-ensemble de la première marche

select = "SELECT" columns "FROM" name [ where ] [ limit ] ; columns = name { "," name } ; where = "WHERE" name operator value ; operator = "=" | "<" | ">" | "<=" | ">=" | "<>" ; value = number | string ; limit = "LIMIT" number ;

Mais dans DESIGN.md, écrivez la grammaire de tout le sous-ensemble visé (JOIN, GROUP BY, HAVING, ORDER BY), même si vous n'en codez qu'une partie.

Quatre briques, une par personne (à trois, A et B vont ensemble)

ALa grammaire

Dans DESIGN.md, la grammaire EBNF du sous-ensemble complet visé, avec des exemples de requêtes acceptées et refusées.

C'est fait quand chacun de l'équipe sait dire si une requête donnée est dans la grammaire.

BLe lexer

Découper une requête en jetons typés (mot-clé, nom, nombre, chaîne, ponctuation), avec leur position.

C'est fait quand des tests couvrent les chaînes entre apostrophes, les nombres et les opérateurs à deux caractères (<=, <>).

CLe parser et l'AST

Une fonction par règle (descente récursive), des dataclasses pour l'arbre, une erreur qui donne la position du jeton fautif.

C'est fait quand 15 requêtes valides sont parsées et 5 invalides rejetées avec un message précis.

DExécution en lecture seule

Ouvrir Chinook avec sqlite3.connect("file:chinook.sqlite?mode=ro", uri=True), n'exécuter que ce que le parser accepte, afficher le résultat.

C'est fait quand un test prouve qu'un DELETE échoue, même envoyé directement à la connexion.

Comment s'y prendre, brique par brique

Une méthode pour démarrer, et des ressources pour aller plus loin. Elles sont en anglais pour la plupart ; un LLM peut vous aider à les lire.

Avec un LLMServez-vous-en pour comprendre : faites-vous expliquer un exemple pas à pas, demandez pourquoi une règle de grammaire boucle, faites relire vos tests. Si un agent écrit du code, relisez-le jusqu'à pouvoir l'expliquer sans lui : le 23, c'est vous qui le défendez.

AConstruire la grammaire

  1. Partir d'exemples. Écrivez 15 à 20 questions réalistes sur Chinook, avec la requête SQL attendue. Relevez les constructions utilisées : c'est votre sous-ensemble, pas plus.
  2. Découper dans la grammaire officielle. SQLite publie la syntaxe de SELECT en diagrammes. Recopiez en EBNF seulement ce qui sert.
  3. Écrire de haut en bas : select, puis une règle par clause, puis les expressions. Une règle par niveau de priorité, du moins prioritaire au plus prioritaire : or_expr, and_expr, not_expr, comparison. Ainsi, a OR b AND c se lit a OR (b AND c).
  4. Éviter la récursion à gauche : expr = expr "AND" expr fait boucler un parser sans fin. On écrit and_expr = comparison { "AND" comparison }. Et à chaque choix, le prochain jeton doit suffire à décider.
  5. Vérifier sur papier : déroulez la grammaire à la main sur chaque exemple, puis sur 5 requêtes qui doivent être refusées.
Pour aller plus loin : syntaxe de SELECT (SQLite) · syntaxe des expressions (SQLite) · la notation EBNF (Wikipédia) · Crafting Interpreters, ch. 5 : les grammaires

BÉcrire le lexer

  1. Lister les types de jetons : mots-clés, noms, nombres, chaînes, opérateurs à un et à deux caractères, ponctuation. Une phrase par type pour dire à quoi il ressemble.
  2. Une boucle sur les caractères : regarder le caractère courant, choisir le type, consommer le jeton entier, noter sa position. Un mot est un mot-clé s'il est dans la liste (sans tenir compte de la casse), sinon c'est un nom.
  3. Les cas pièges : une apostrophe dans une chaîne s'écrit '' en SQL ('l''été') ; après <, regarder si vient = ou > ; un caractère inconnu donne une erreur avec sa position.
  4. Tester avec un tableau : des couples (texte, jetons attendus), parcourus par un seul test paramétré.
Pour aller plus loin : Crafting Interpreters, ch. 4 : Scanning · Let's Build A Simple Interpreter, en Python (parties 1 à 3) · pytest : tests paramétrés

CÉcrire le parser et l'arbre

  1. Concevoir l'arbre d'abord. Une dataclass par construction : Select, Column, Literal, BinaryOp… Les expressions forment un seul type : Expr = Column | Literal | BinaryOp. Dessinez l'arbre de 3 de vos exemples avant d'écrire du code.
  2. Une méthode par règle, avec trois outils : peek() (le jeton courant), match() (le consomme s'il convient), expect() (le consomme ou lève une erreur avec la position). { … } devient une boucle while, [ … ] un if.
  3. Tester en comparant des arbres : parse("…") == Select(...). Les dataclasses se comparent champ par champ.
  4. Le test aller-retour, le plus puissant : une fonction qui réécrit l'arbre en SQL, et la vérification parse(to_sql(arbre)) == arbre. sqlglot peut servir de juge dans les tests (même verdict, accepté ou refusé), jamais dans votre code.
Pour aller plus loin : Crafting Interpreters, ch. 6 : Parsing Expressions · Let's Build A Simple Interpreter, partie 7 : l'AST · Python : dataclasses · Python : le module ast, un vrai AST · Hypothesis · sqlglot

DExécuter sans risque

  1. Récupérer la base : le fichier SQLite de Chinook, dans le dépôt GitHub lerocha/chinook-database. Ouvrez-le une fois avec l'outil sqlite3 pour regarder les tables.
  2. Ouvrir en lecture seule avec une adresse de fichier (URI) : file:chinook.sqlite?mode=ro et uri=True. Ajoutez PRAGMA query_only = ON.
  3. N'exécuter que ce que le parser a accepté : la commande run appelle le parser d'abord, et s'arrête à la moindre erreur.
  4. Tester chaque barrière seule : un test qui envoie un DELETE au parser, un autre qui l'envoie directement à la connexion.
Pour aller plus loin : Chinook · Python : sqlite3 · SQLite : les adresses URI et mode=ro

3Et ensuite : la séance du 23 novembre

Le 23 novembre, la séance porte sur l'architecture : comment découper ce système en morceaux de code, qui dépend de qui, comment tester chaque morceau sans les autres. On y réfléchira ensemble, en séance : rien à préparer de ce côté. Voici seulement le schéma global de ce qu'on va construire, pour vous situer.

Trois mots qu'on utilisera le 23Un composant est un morceau du programme (un module, une classe) qui a une responsabilité : une seule chose qu'il sait faire. Une dépendance, c'est quand un composant a besoin d'un autre pour fonctionner.
